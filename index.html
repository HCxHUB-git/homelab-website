02

Hardware

The machines that implement the lab. Specs below are the ones verified in the public record, with owner-supplied identification where the audit could not read it from the hardware.

Edge router

The ISP router was replaced because it limited control of DNS and advanced configuration. Those limits were owner-observed and not independently audited. OpenWrt now sits behind the optical handoff and reproduces the ISP WAN requirements: VLAN 100, DHCP IPv4, routing, NAT, and firewalling. The router’s own Wi-Fi radios are disabled. An external access point serves wireless clients. The router DNATs one inbound UDP flow to WireGuard and does not terminate the VPN itself.

  • ARM64, Mediatek Filogic
  • 10 GbE SFP WAN and a separate 10 GbE SFP LAN
  • Copper LAN ports present; no carrier at review
  • OpenWrt snapshot, kernel 6.6

Virtualization host

One Proxmox node, with no cluster high availability. LXC is the operating boundary and most containers are unprivileged. Docker is the application boundary inside dedicated LXCs. Native services — Jellyfin, Pi-hole, and WireGuard — run directly in their containers. Local NVMe holds the hypervisor, swap, and guest disks. Bulk data does not. The chassis is owner-identified; DMI strings were empty in the audit. One copper NIC is bridged on vmbr0 for management and guest traffic.

  • Intel i9-13900HK, 14 cores / 20 threads
  • 1 TB Kingston NVMe, LVM-thin guest disks
  • Intel iGPU for Quick Sync
  • Linux kernel 6.8, single node

Storage server

TrueNAS SCALE 25.04 holds media, cloud data, photographs, and backups, and serves them over NFS and SMB. The data disks are two WD Ultrastar-class drives and two Seagate IronWolf-class drives. The two 2.5 GbE interfaces use a TrueNAS LOADBALANCE software bond configured on the storage host. That is not switch-side aggregation, not LACP, and not a claim of 5 Gb/s to a single client. Distribution and failover are still validation items.

  • Intel N150, about 16 GiB, non-ECC
  • 4 × 8 TB 7200 RPM in RAIDZ1
  • 512 GB NVMe for the system disk
  • 2 × 2.5 GbE in a host-side bond

Switch and wireless

The unmanaged switch is the single downstream layer between the OpenWrt LAN uplink and the compute host, the storage server, the access point, and other clients. It has no telemetry, VLAN, or aggregation capability, and none is claimed. The Omada access point provides every Wi-Fi client. SSIDs, radio policy, VLAN assignment, and client isolation on the access point were not verified.

  • UGREEN CM753 unmanaged switch
  • Downstream of the 10 GbE LAN uplink
  • TP-Link Omada access point
  • All Wi-Fi clients terminate here

Network and security

The edge router, remote access, acquisition egress, and how a hostname reaches a private service.

  1. ISP fibre→
  2. VLAN 100→
  3. OpenWrt→
  4. NAT and firewall→
  5. 10 GbE LAN

OpenWrt owns WAN configuration, routing, NAT, firewall policy, DNS and DHCP integration, and port forwarding. Pi-hole is the LAN DNS and DHCP authority for IPv4 and IPv6, so OpenWrt’s LAN DHCP is disabled. WAN input rejects by default. The IPv6 WAN path was inactive at review. The LAN is still flat: there are no service VLANs yet, which leaves a path for later segmentation.

  1. Remote client→
  2. Internet→
  3. OpenWrt→
  4. UDP DNAT→
  5. WireGuard LXC→
  6. Private services

WireGuard runs in a dedicated container. The edge router forwards a single inbound UDP flow and does not terminate the tunnel. Encrypted access reaches private services without publishing each backend on its own port. This path is separate from the Mullvad egress used for media acquisition.

  1. qBittorrent→
  2. Gluetun→
  3. Mullvad→
  4. Internet

Gluetun is an application-level VPN boundary for the media acquisition workflow. qBittorrent’s traffic leaves through Mullvad. The rest of the homelab is not routed through that VPN. Remote access and this egress path are different tunnels with different jobs.

  1. service.hcxhub.com→
  2. Cloudflare→
  3. Pi-hole→
  4. Nginx Proxy Manager→
  5. Internal service

The zone is managed in Cloudflare. On the LAN, Pi-hole resolves names such as proxmox.hcxhub.com, grafana.hcxhub.com, immich.hcxhub.com, and homarr.hcxhub.com. Nginx Proxy Manager maps each hostname to an internal backend, so operators use names instead of memorized addresses and ports. Services stay on private and VPN-reachable paths. The hostname is how the service is reached inside that boundary.

WAN

ISP fibre, VLAN 100, DHCP IPv4, NAT, WAN input reject. IPv6 WAN path inactive at review.

LAN

10 GbE backbone, flat LAN, no service VLANs yet. Router Wi-Fi radios disabled.

DNS and DHCP

Pi-hole is the authority for IPv4 and IPv6. OpenWrt LAN DHCP is disabled.

Wireless

External Omada access point serves all Wi-Fi clients.

Storage network

Two 2.5 GbE endpoints in a host-side software bond on TrueNAS.

04

Services

What each service is for, why it is set up this way, how it is deployed, and how a request moves through it.

Daily

Nextcloud

Private file storage and synchronization across devices, with access from the browser.

Why

Files stay on hardware the lab controls, in the same pattern as the rest of the private services: useful every day, and independent of a hosted drive.

How it is implemented

Docker inside a dedicated LXC, with MariaDB and Redis beside it. Application and user data persist on NAS-backed storage over NFS, not inside the container root, so the guest can be rebuilt without taking the library with it.

How it works

Clients sync to Nextcloud. The app talks to MariaDB for state and Redis for caching. File data is written to the TrueNAS dataset exported over NFS. The hostname reaches it through Nginx Proxy Manager.

  • Nextcloud
  • MariaDB
  • Redis
  • Docker in LXC
  • NFS
  • TrueNAS / ZFS

Daily

Immich

Self-hosted photographs and video. Phones back up automatically into one library that can be browsed, searched, and organized.

Why

The photo library is personal data with the same requirement as the file cloud: one place, on the NAS, not a third-party gallery.

How it is implemented

Docker in an LXC. PostgreSQL with pgvector stores metadata and search features, Valkey handles cache and queues, and a machine-learning worker runs alongside the app. The library itself is on NFS from TrueNAS.

How it works

A phone upload lands in Immich. The database records it, the ML worker generates search features, and the original files stay on the ZFS dataset. Browsing uses the internal hostname.

  • Immich
  • PostgreSQL / pgvector
  • Valkey
  • ML worker
  • Docker in LXC
  • NFS

Daily

Vaultwarden

Self-hosted password vault for the accounts used across the lab and everyday devices.

Why

Passwords are kept with the rest of the private services, reached only through the LAN reverse proxy or remote access, rather than a public signup.

How it is implemented

Its own unprivileged LXC. Docker Compose runs Vaultwarden with SQLite on the guest’s local disk, and that guest is included in the daily Proxmox backup. Account onboarding and the post-enrollment registration lock are still to be verified.

How it works

Clients connect over HTTPS. Nginx Proxy Manager presents the hostname and forwards to the container. The vault file lives on the guest disk, so recovery depends on the guest backup rather than the NAS dataset used by Nextcloud and Immich.

  • Vaultwarden
  • Docker Compose
  • Unprivileged LXC
  • SQLite
  • LAN ingress
  • Guest backup

Media

Jellyfin

The media library, streamed to TVs, browsers, computers, and phones.

Why

Transcoding stays in an isolated service. The media server is not installed on the hypervisor, and only the Intel render device is passed through.

How it is implemented

Native systemd service in its own LXC, with Intel Quick Sync. A pre-start hook restores device ownership on every host boot, because permissions could otherwise break silently after a restart. The HTTP health endpoint was verified after that boot path.

How it works

The library is the NFS share on TrueNAS. Jellyfin reads it and transcodes with the iGPU when a client needs a different format. Hardware acceleration survives a reboot because the hook runs before the service starts.

  • Jellyfin
  • Native in LXC
  • Intel Quick Sync
  • NFS library
  • Pre-start hook

Media

Media automation

Request, find, acquire, and file television and movies into the library Jellyfin already serves.

Why

Acquisition is one workflow with its own egress. It is not how the rest of the homelab reaches the internet.

How it is implemented

One media-automation LXC runs the Docker stack: Jellyseerr, Sonarr, Radarr, Prowlarr, Bazarr, Recyclarr, qBittorrent, Gluetun, FlareSolverr, and changedetection. They share the NFS library on TrueNAS. At review, the containers were up and Gluetun was healthy.

How it works

A request enters through Jellyseerr. Sonarr handles series and Radarr handles films. Prowlarr manages indexers, with FlareSolverr available for challenges. qBittorrent downloads through Gluetun to Mullvad. Finished files land on the NAS. Bazarr handles subtitles, Recyclarr keeps quality profiles, and Jellyfin streams the result.

  • Jellyseerr
  • Sonarr
  • Radarr
  • Prowlarr
  • qBittorrent
  • Gluetun
  • Bazarr
  • NFS

Network

Pi-hole

DNS filtering, internal naming, and DHCP for the whole LAN.

Why

The router is no longer the place that hands out leases or answers local DNS. One service is the authority, which is what made the ISP router replaceable.

How it is implemented

Pi-hole FTL runs as a native systemd service in an LXC, with local SQLite databases. It listens for DNS and DHCP on IPv4 and IPv6. OpenWrt’s LAN DHCP is off. The long-term query database once filled the guest disk with free SQLite pages that had not been returned to the filesystem.

How it works

Clients learn Pi-hole from DHCP. Queries are filtered and, for lab hostnames, answered locally. Records that should be public resolve through the Cloudflare-managed zone. DHCP leases come from Pi-hole, not the edge router.

  • Pi-hole FTL
  • Native in LXC
  • SQLite
  • DNS
  • DHCP
  • IPv4 and IPv6

Network

WireGuard

Encrypted remote access to the private services.

Why

Terminating the VPN in its own container keeps the router’s job small: forward one UDP flow. Backends are not exposed one by one.

How it is implemented

A dedicated LXC runs WireGuard. OpenWrt DNATs the inbound UDP flow to that container and nothing else on the WAN is opened for the services behind it.

How it works

A remote client brings up the tunnel. Traffic arrives at the WireGuard container, then reaches LAN services as if the client were on the network. Ingress hostnames still resolve, and the services stay off the public internet.

  • WireGuard
  • Dedicated LXC
  • UDP DNAT
  • OpenWrt

Network

Nginx Proxy Manager

One ingress for application hostnames.

Why

Backend addresses change. The name a person types should not. Centralizing that map keeps every service from publishing its own port.

How it is implemented

Nginx Proxy Manager terminates the friendly hostnames and proxies them to internal backends. The public DNS zone is on Cloudflare. On the LAN, Pi-hole is what resolves those names.

How it works

A request for immich.hcxhub.com is answered by Pi-hole, arrives at the proxy, and is forwarded to the Immich container. The same pattern covers Proxmox, Grafana, Homarr, and the other named services.

  • Nginx Proxy Manager
  • Cloudflare DNS
  • Pi-hole
  • Internal backends

Platform

Prometheus and Grafana

Metrics for applications, the storage server, and disk health.

Why

Troubleshooting starts from what was scraped, not from a guess about which layer failed.

How it is implemented

Prometheus scrapes application health endpoints, TrueNAS node metrics, and SMART exporters. Grafana dashboards show infrastructure and storage state. Scrape targets were healthy at review. Alert routing and delivery are not validated yet.

How it works

Exporters publish metrics. Prometheus stores them. Grafana reads Prometheus. The same panels — memory, CPU, disk temperature, network — are also surfaced on the Homarr dashboard.

  • Prometheus
  • Grafana
  • node exporter
  • SMART exporter
  • TrueNAS

Homarr

The visual front door: service tiles plus the widgets already used day to day.

Why

It is an application for people opening the lab, not a network control plane. DNS, DHCP, VPN, and ingress stay in their own services.

How it is implemented

Homarr runs as its own application behind homarr.hcxhub.com. Storage, monitoring, and Pi-hole statistics are shown as widgets on that board.

How it works

Opening the hostname shows the tiles. Each tile links to the real service. The widgets read the same monitoring and DNS data the rest of the stack already collects.

Platform

Hermes

An experimental, LLM-driven assistant for systems administration tasks.

Why

The lab is also where operational tooling gets tried. The assistant has to be able to help without becoming the thing that changes production on its own.

How it is implemented

Hermes runs in a dedicated LXC, with Python, Node.js, an LLM integration, and tools aimed at infrastructure tasks. It is isolated from the services it might be asked about.

How it works

An operator asks for help with a task. Hermes can use its tools to inspect or assist. It does not autonomously manage the infrastructure.

05

Storage and backup

Compute disks and bulk data are separate. ZFS holds the data. Proxmox guest backups land on the same storage server.

Compute storage

Proxmox’s local NVMe holds the hypervisor, swap, and LVM-thin guest disks. Latency-sensitive system and container workloads stay on that disk.

Bulk data

TrueNAS centralizes media, cloud files, photographs, and backups, and serves them over NFS and SMB. Containers stay replaceable. The data they use does not live only inside the guest.

Why ZFS

The requirements were long-term integrity, point-in-time rollback, one manageable pool, and operational visibility. ZFS covers checksums, snapshots, pool management, scrubs, compression, and RAIDZ without a hardware RAID controller. The trade-off is that memory and power stability matter, and a pool is not as portable as a plain filesystem.

Why RAIDZ1

Four disks, one fault tolerated, and three disks of usable capacity. A wider parity layout would spend capacity this environment does not yet need. RAID keeps the pool available through a disk failure. It is not a backup. Snapshots roll back logical mistakes. Backups cover other failures. Today the primary data and the local backup copies share one physical failure domain.

  • Snapshots

    Daily recursive ZFS snapshots, kept for four weeks, for short-term rollback.

  • Scrubs

    Periodic verification of the pool against ZFS checksums.

  • SMART

    Drive health: a short test every week and a long test every quarter.

  • Guest backups

    Proxmox snapshot-mode archives, zstd compressed, keep-last 7, written to TrueNAS. Recent tasks and retained generations were verified.

06

Operations

Health is checked along the chain: listener, process, application, database, mount, then network and storage. Installed is not the same as operated.

Monitoring

Prometheus and Grafana, TrueNAS node and SMART exporters, application health endpoints.

Alert routing and delivery are not validated.

Data protection

Daily ZFS snapshots for four weeks, periodic scrubs, weekly short and quarterly long SMART tests.

Datasets are not encrypted at rest. No UPS was observed.

Backup

Daily Proxmox guest archives, zstd, keep-last 7, on NAS backup storage. Recent tasks succeeded.

No off-site copy. No completed restore drill.

Access and security

WAN input reject, WireGuard remote access, mostly unprivileged LXCs, separate VPN egress for acquisition.

Flat LAN, broad management listeners, and password root SSH on the router.

Engineering work

Changes that were audited, applied carefully, and checked again. Problem, what was found, what was changed, and what the re-check showed.

Problem

Zone policy overrode the safer global input default, so WAN input was ACCEPT. LAN masquerading was enabled without a verified need.

Investigation

The effective nftables rules were audited before anything was changed.

Decision

A focused LuCI change: WAN input to REJECT, and LAN masquerading off. Routing, NAT, the WireGuard DNAT, and Pi-hole were left in place and checked again.

Result

The re-audit matched the intended policy. WAN NAT, LAN-to-WAN forwarding, the VPN forward, and DNS still worked.

Lesson

Installed security tooling is not evidence of effective policy. The rule path has to be read.

Problem

Hardware transcoding was required without placing the media server on the hypervisor, and render-device permissions could fail silently after a host restart.

Investigation

The failure showed up on the boot path, not while the host had been left running.

Decision

Pass through only the Intel render device, and restore its ownership with an idempotent pre-start hook on every boot.

Result

Quick Sync transcoding runs in the isolated LXC. The health endpoint succeeded after the boot path.

Lesson

Reboot recovery is part of the service, not a follow-up task.

Problem

The Pi-hole root filesystem hit 80 percent. Logs did not explain it.

Investigation

SQLite page accounting showed about 91 percent of the long-term query database was internally free and had not been returned to the filesystem.

Decision

Treat retention and compaction as different controls. Plan headroom, a backup, and a controlled compaction instead of an unsafe in-place vacuum.

Result

The capacity problem was identified as free pages inside the database file, not as a logging leak.

Lesson

Logical retention and physical compaction are separate controls.

Problem

A backup job configured in the interface only proves that a job exists.

Investigation

Scope, recent task status, the archives themselves, and retention were checked independently of the schedule screen.

Decision

Keep the daily zstd guest backup, seven generations, on the NAS — and write down what that does not cover.

Result

Recent successful tasks and retained generations were verified. There is still no restore drill and no off-site copy. Primary data and these backups share one site.

Lesson

A schedule proves intent. Recovery is a restore that has been done.
