Network

Replacing the ISP router · OpenWrt

Problem: the ISP-provided router limited control over the local network — owner-observed limits around DNS behavior and advanced configuration (not independently audited).

Decision: replace it with a fully controlled OpenWrt edge router behind the optical handoff, reproducing the ISP WAN requirements: VLAN 100, DHCP IPv4, routing, NAT and firewalling.

Result: full control over WAN configuration, routing, NAT, firewall policy, DNS/DHCP integration, port forwarding and a path to future VLAN segmentation — with Pi-hole as the LAN DNS/DHCP authority.

Storage architecture

Compute and persistent data are deliberately separated.

Compute storage

Proxmox local NVMe holds the hypervisor, swap and LVM-thin guest disks — latency-sensitive system and container workloads stay local.

Persistent / bulk data

A dedicated TrueNAS storage server centralizes growing datasets (media, cloud, photos, backups) and serves them over NFS/SMB. Containers stay comparatively disposable while persistent data lives independently, with its own monitoring and maintenance.

Supporting mechanisms: LZ4 compression · ZFS snapshots (daily, 4-week retention) · periodic scrubs · SMART monitoring.

Why ZFS

Requirements: long-term data integrity, point-in-time rollback, one manageable pool, operational visibility. ZFS answers them in one layer — end-to-end checksumming, integrated snapshots and pool management, scrubbing, compression and RAIDZ without a hardware controller.

Trade-off: memory and power stability matter, and a pool is not portable like a plain filesystem.

Why RAIDZ1

With four disks, RAIDZ1 tolerates one disk failure while keeping three disks' worth of usable capacity — higher parity would cost capacity this environment does not yet need.

RAID IS NOT BACKUP.

RAID improves availability against disk failure. Snapshots roll back logical errors. Backups address different failures — and today primary data and local backups share one failure domain.

Snapshots · scrubs · SMART

  • Snapshots — short-term rollback points (daily recursive, 4-week retention).
  • Scrubs — periodic ZFS integrity verification against checksums.
  • SMART — drive-health monitoring: weekly short, quarterly long tests.

NAS networking — stated limits

Two 2.5 GbE interfaces in a TrueNAS LOADBALANCE software bond supply the NFS/SMB path. No 5 Gb/s single-client throughput, no switch-side aggregation and no LACP are claimed; distribution and failover behavior remain validation items.

Problem: hardware transcoding was needed without putting the media server on the hypervisor, and device permissions could break silently after a host restart. Decision: pass only the Intel render device; add an idempotent pre-start ownership hook. Result: hardware-accelerated transcoding in an isolated service; health endpoint verified after the boot path. Lesson: reboot recovery is part of the service contract.

Case notes

DNS capacity diagnosis

Pi-hole's root filesystem hit 80% — logs didn't explain it. SQLite page accounting showed ~91% of the long-term query database was internally free but not returned to the filesystem. Resolution planned with headroom, backup and controlled compaction instead of an unsafe in-place vacuum. Lesson: logical retention and physical compaction are separate controls.

Case notes

Backup confidence

A schedule in a UI proves intent, not recovery. Scope, recent task status, artifacts and retention were verified independently — and the remaining gap (no restore drill, no off-site copy) is documented rather than glossed over.
